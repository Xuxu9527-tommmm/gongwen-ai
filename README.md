# gongwen-ai 公文 AI 核心能力库

> 让 4B 的小模型也能写出"像样"的公文——靠的不是模型大小，是**规矩**。
>
> 一套完全离线的公文知识工程：**20 个文种知识卡 + 自动判文种 + 11 类确定性核稿 + GB/T 9704 版式参数**。不联网、不调外部 API、可嫁接到任何本地模型（Ollama / llama.cpp）或在线模型。

**本仓库不含任何模型文件**（模型体积大、许可证各异，不适合放进 Git）。模型由使用者自行下载，放到本地即可——推荐 **4B 级别**，普通办公电脑就能跑，不需要显卡。

## 为什么开源这个

公文写得像不像，靠的不是模型大小，是「规矩」。规矩分三类：

| 类别 | 例子 | 处理方式 |
|---|---|---|
| ① 文种规矩 | 15 种法定文种各有结构、要素、结语 | **可枚举 → 做成知识卡注入** |
| ② 版式规矩 | GB/T 9704-2012 字体字号页边距 | **可枚举 → 导出时确定性落地** |
| ③ 提法规矩 | 政策表述有时效性 | **只能人核，机器不碰** |

①②是可以枚举、可检索、可校验的。做成**外挂知识库**比"训进模型"更准：

- 每次只注入当前文种那一张卡（**≤450 字**），4B 模型也吃得透；
- 核稿走**确定性规则**：毫秒级、100% 可复现、不烧 token、不会胡说。

这套思路已在真实产品中验证：一个小模型 + 本知识库，写出的通知、请示、报告被机关老笔杆认可，核稿能抓住"请示报告"混用、序号跳级、结语错配、发文字号括号错误等硬伤。

## 能不能在你的电脑上跑

先分清两件事，门槛完全不同：

| 形态 | 要什么 | 门槛 |
|---|---|---|
| **A. 只用知识层**（文种卡 / 判文种 / 核稿） | 一个浏览器，或 Node ≥14 | **几乎没有**。断网可用，老机器可用，国产系统、龙芯、申威都能跑 |
| **B. 接本地模型出稿** | 再加推理引擎 + 模型文件 | 4 核 CPU / 8GB 内存 / 5GB 磁盘，**不需要独立显卡** |

下面这张表说的是**形态 B**（本地出稿）。形态 A 不挑系统和 CPU 架构，只要能开浏览器就成立。

### 国产操作系统支持情况

国产生态碎片化严重，这里把"实测过的"和"还没试过的"分开写清楚，不含糊：

| 系统 | 架构 | 状态 | 说明 |
|---|---|---|---|
| Windows 10 / 11 | x64 | **已实测** | 主力平台，日常验证都在这里做 |
| Windows 10 / 11 | ARM64 | **已验证**（静态核验） | 骁龙本可跑，未做长时间压测 |
| 银河麒麟 V10 桌面版 | x64 | **已验证** | 实机运行通过 |
| 银河麒麟 V10 桌面版 | arm64 | **已验证** | 飞腾 / 鲲鹏平台 |
| 统信 UOS 20 | x64 | **已验证** | 实机运行通过 |
| 统信 UOS 20 | arm64 | **已验证**（qemu） | 虚拟机验证，未上真机 |
| macOS 13+ | Intel / Apple Silicon | **已验证**（静态核验） | |
| 深度 Deepin 20 / 23 | x64 | **待验证** | 与 UOS 同源，预期可用，但**我没测过** |
| 开放麒麟 openKylin | x64 | **待验证** | 同上，未测 |
| 中科方德 / 麒麟信安 | x64 | **待验证** | 未测 |
| 龙芯 LoongArch | loongarch64 | **当前不支持** | 无预编译引擎，需自行用 llama.cpp 源码编译 |
| 申威 | sw_64 | **当前不支持** | 上游无支持，社区也无可用移植 |

**怎么看这张表**：写"已验证"的，我实际跑过；写"待验证"的，理论上没问题但**没有证据**，你装了跑不起来属正常情况，欢迎到 Issues 反馈实测结果，我会补进这张表；写"不支持"的，是确实没路走，不用试了。

> 麒麟 / UOS 上如果报 `GLIBC_2.xx not found`，说明系统库版本低于预编译引擎的要求，改用源码编译 llama.cpp 即可，知识层（形态 A）不受影响。

## 模型：本仓库不含，需要你自己下载

**为什么不在仓库里放模型**

- 一个 4B 的 GGUF 量化模型 2~3GB，Git 仓库放不下也不该放；
- 模型许可证各不相同（Apache-2.0 / 社区协议 / 商用限制），混进代码仓库会带来授权麻烦；
- 模型迭代比代码快，绑死版本反而不好用。

**推荐配置（这是"低门槛"的关键）**

| 项 | 建议 | 说明 |
|---|---|---|
| 模型 | **Qwen3-4B-Instruct**（GGUF，Q4_K_M 量化） | 约 2.5GB。中文公文语料充足，指令跟随稳，4B 是这个任务上的甜点 |
| 备选 | Qwen2.5-3B-Instruct / Gemma-3-4B | 内存更紧张（4GB）时用 3B；英文混排多时试 Gemma |
| 硬件 | 4 核 CPU / 8GB 内存 / 5GB 空闲磁盘 | 老办公本、核显、无独显都可以 |
| 引擎 | llama.cpp（`llama-server`）或 Ollama | 两者都行，Ollama 更省事 |

**下载（国内直连慢就用镜像）**

```bash
# 方式一：Hugging Face 镜像站（国内推荐）
# 打开 https://hf-mirror.com ，搜索 Qwen3-4B-Instruct-GGUF
# 下载文件名带 Q4_K_M 的那一个，约 2.5GB

# 方式二：Ollama 一条命令（自动处理路径，最省事）
ollama pull qwen3:4b
```

**放到哪**（下面只是示例，目录结构由你决定。**本仓库不含 `引擎/` 和 `models/` 这两个目录**，它们是你自己准备的）

```
你的工作目录/
├── models/
│   └── Qwen3-4B-Instruct-Q4_K_M.gguf    ← 模型放这里
└── 引擎/
    └── llama-server                      ← 引擎放这里
```

用 llama.cpp 启动时把上下文压到 4096 就够（文种卡只有 450 字，不需要长上下文，压小反而更快）：

```bash
./llama-server -m models/Qwen3-4B-Instruct-Q4_K_M.gguf \
  -c 4096 -t 4 --host 127.0.0.1 --port 8080
```

**为什么 4B 就够——不是模型强，是活被拆走了**

普通电脑跑 4B 模型，最怕两件事：写不长、写着写着跑题。这个项目把这两件事都从模型身上拿走了：

1. **结构不靠模型记**：文种卡把"分几段、每段写什么、结尾怎么收"固定下来，模型只负责填内容，不负责想结构；
2. **合规不靠模型判**：核稿是 11 类确定性规则，毫秒级跑完，跟模型大小无关，4B 和 70B 查出来一样；
3. **上下文不浪费**：每次只注入当前文种那 450 字，4096 的窗口绰绰有余，不用为了塞提示词牺牲速度。

结果就是：**4B 模型 + 本知识库 ≈ 大模型裸写**的成稿质量，而硬件门槛降到一台普通办公本。速度取决于你的 CPU 核数，实机跑一遍才知道，但交互式出稿是没问题的。

> **关于"优化和训练"**：配套产品侧做过 llama.cpp 的 CPU 推理优化，也针对公文语料做过调优。但**模型权重和引擎都不在本仓库**——这里只开源"规矩"这一层。理由很实际：权重你下载现成的就行，而规矩（文种卡、核稿规则、版式参数）才是可读、可改、可审计、可替换的部分，也最值得社区一起补。

## 快速开始

### ① 双击体验（零依赖）

用浏览器打开 [`web/demo.html`](web/demo.html)——单文件、纯前端、不联网：

- **文种卡**：浏览 20 个文种的结构、必备要素、易错点
- **判文种 + 核稿**：粘一段稿子，自动判文种并出核稿报告

### ② 命令行（需 Node ≥14）

```bash
git clone https://github.com/Xuxu9527-tommmm/gongwen-ai.git
cd gongwen-ai

node cli/cli.js list                          # 列出全部文种
node cli/cli.js card tongzhi                  # 打印「通知」文种卡
node cli/cli.js detect examples/请示-有硬伤.txt # 判文种 → qingShi（请示）
node cli/cli.js check examples/请示-有硬伤.txt  # 确定性核稿
```

核稿输出示例（对 `examples/请示-有硬伤.txt`，5 处硬伤全部命中）：

```
查出 5 处硬伤、1 处提醒（文种：请示）

1. 【必须改】标题
   「请示报告」不是法定文种。
   → 要批准改「请示」，只汇报改「报告」

2. 【必须改】主送机关
   请示只能主送一个上级机关，不能多头主送。
   → 只保留一个主送机关，其他放抄送
   ...
```

### ③ 接到本地模型上出稿

```bash
# 启动 Ollama（或任何 OpenAI 兼容服务：llama.cpp server / vLLM / LM Studio）
ollama serve

# 文种卡注入 + 出稿：先取卡，再当 system prompt 的一部分
CARD=$(node cli/cli.js card qingShi)
curl -s http://127.0.0.1:11434/v1/chat/completions -H "Content-Type: application/json" -d "$(node -e "
const card = process.argv[1];
const user = '帮各单位培训基地写一份请示：下半年想办一期基层业务培训班，预算大概8万，培训对象是全体基层人员。';
console.log(JSON.stringify({
  model: 'qwen3:4b',
  messages: [
    { role: 'system', content: '你是机关公文写作专家。严格按下面文种卡的结构写，小标题一字不改；用户没给的信息一律写「××」，绝不编造。\n' + card },
    { role: 'user', content: user }
  ]
}))" "$CARD")" | jq -r '.choices[0].message.content'
```

写完把稿子喂回 `node cli/cli.js check` 就是自动核稿闭环。完整脚本见 [`examples/本地出稿-闭环.sh`](examples/本地出稿-闭环.sh)。

## 核心概念：文种卡（Genre Card）

每个文种一张卡，字段固定：`use`（适用）/ `no`（不适用）/ `struct`（结构模板）/ `must`（必备要素）/ `end`（规范结语）/ `trap`（易错点）/ `len`（篇幅区间）。

写稿时**只注入当前那张**（`GW.cardText(id)`，压到 ≤450 字）——这是小模型能跟住结构的关键：全量塞 20 张卡，4B 模型会串文种；只给一张，结构跟得很稳。

判文种（`GW.detect(text)`）用关键词加权打分：标题区命中权重 6、正文 2、文种名收尾再 +10；分数过低返回 `null` 交还用户，**宁可问也不猜**。

## 确定性核稿（11 类规则）

| # | 检查项 | 级别 |
|---|---|---|
| 1 | 标题：句号、超长、"请示报告"伪文种、有"关于"无文种 | err/warn |
| 2 | 主送机关：缺冒号、请示多头主送 | warn/err |
| 3 | 结语与文种匹配（通知↔特此通知，请示↔妥否请批示…） | err |
| 4 | 请示夹带报告 / 报告夹带请示 / 一文一事 | err/warn |
| 5 | 层次序号跳级（一、→（一）→1.）、「1.」与「1、」混用 | err/warn |
| 6 | 成文日期：汉字数字、前导零、套往年模板 | err/warn |
| 7 | 发文字号必须六角括号〔〕；半角标点 | err/warn |
| 8 | 语气：感叹号、函用下行口气 | warn |
| 9 | 空话密度（高度重视×3、狠抓落实…） | warn |
| 10 | 「××」占位符统计 | warn |
| 11 | 篇幅超文种区间 1.8 倍 | warn |

规则设计原则：**只报确定的问题，不写条款号**（模型和人一样记不准"GB/T 9704 第几条"，写了反而误导）。详见 [`docs/CHECK_RULES.md`](docs/CHECK_RULES.md)。

## 接入你的应用

```html
<script src="core/gongwen.js"></script>
<script>
  GW.detect(text)            // → 'qingShi' | null
  GW.cardText('qingShi')     // → 文种卡文本（注入 system prompt）
  GW.check(text, 'qingShi')  // → [{lv:'err', at:'标题', msg:'…', fix:'…'}]
  GW.checkText(list, gid)    // → 给人看的核稿报告
  GW.groups() / GW.get(id)   // → 分组与文种详情
</script>
```

零依赖、单文件、浏览器 / Node 通用（Node 下先 `global.window = {}` 再 require）。

## 能力边界

开源项目最怕"看起来什么都能干"。这里把话说死，**哪一行不满足你的预期，就是这项目不适合你**。

### 能做，而且做得比较稳

| 能力 | 说明 |
|---|---|
| 判文种 | 给出稿子，判断该走请示 / 报告 / 通知 / 函……；判不准时返回 `null` 让人选，**不瞎猜** |
| 结构骨架 | 按文种卡给出分段、要素、结语，写出来是"公文的样子"而不是"作文的样子" |
| 格式硬伤 | 标题带句号、"请示报告"混用、主送多头、结语错配、序号跳级、日期写法、发文字号括号——**确定性查，不漏不误报** |
| 语气与水分 | 感叹号、下行口气用在函上、"高度重视×3""狠抓落实"这类空话密度 |
| 版式参数 | GB/T 9704-2012 的字体字号页边距，导出时可直接落地 |

### 做不好，必须有人接手

| 场景 | 实际情况 |
|---|---|
| 长稿（>2000 字） | 后半段结构会漂，**分段写再拼**比一次生成靠谱 |
| 数字、金额、人名、地名、机构名、文件号 | 4B 模型会编。**规矩是：用户没给的一律写 ××**，由人填，别指望它猜对 |
| 政策依据、上级文件引用 | 不做。这类内容有时效性和层级关系，机器给的一定是错的或过时的 |
| 地方表达习惯 | 卡里是通用写法，省市县的行文习惯差异得自己调 `core/gongwen.js` |
| 会议纪要的惯用语 | "会议认为""会议指出"这类套话覆盖不全，需要补充 |

### 明确不做

- **不判密级、不做保密审查**——这是保密部门的活，工具不碰；
- **不替代签发**——出的是草稿，签发责任在人；
- **不保证政策时效**——昨天对的提法今天可能就改了；
- **不做事实核查**——它不知道你的数据是不是真的。

### 一句话判断适不适合你

> 适合：**格式规范、结构完整、语言得体**这件事占了你大量时间，你愿意花 5 分钟核对事实和数字。
>
> 不适合：想让 AI 直接出终稿、想让它自己找政策依据、想拿它过保密审查。

**免责声明**：本工具只做格式与结构层面的确定性检查。政策提法、数字口径、涉密内容必须由本单位核稿人终审。使用本工具产生的文稿，其内容真实性、合规性由使用者负责。
